# NOVA Data and Claims Policy

## Purpose

NOVA is a portfolio project for the fictional Northstar Charge Network. Its operating records are synthetic. The project may optionally use public information to provide environmental or geographic context, but public context must never be presented as Northstar operations and must never make the deterministic synthetic MVP depend on a live external service.

This document defines the two permitted data classes, their provenance requirements, snapshot and licensing records, synthetic-row labeling, and the evidence required for portfolio or resume claims.

## Data classification

Every source, table, file, model feature, API response, and materialized analytical output must be traceable to one or both of these classes:

1. **PUBLIC CONTEXT** — externally published information used only to describe the environment in which the fictional network operates.
2. **SYNTHETIC OPERATIONS** — generated records describing the fictional network's assets, customers' anonymous charging activity, operating events, commercial behavior, maintenance, inventory, and suppliers.

These classes may be joined for analysis, but they must not be blended into an unlabeled third category. A derived row inherits all applicable provenance. An output that combines public weather with synthetic sessions remains a synthetic operational analysis enriched by public context; it is not evidence about the performance of a real charging network.

## PUBLIC CONTEXT

### Permitted uses

Public context may include the following when practical and when an official or otherwise authoritative source has suitable access and reuse terms:

- Official EV charging-station locations and non-sensitive station attributes.
- Historical weather observations or forecasts associated with a station area and time.
- Public electricity or energy-price context, such as regional or state-level historical prices.
- Stable geographic attributes needed to map locations or assign time zones.

Public context is optional and belongs to the Advanced tier described in `docs/SCOPE.md`. The MVP must run from a clean checkout using deterministic synthetic substitutes when public data is absent, a source is unavailable, or network access is disabled.

### Boundaries

- A public station location does not imply that Northstar owns, operates, prices, or services that station.
- Public price context is not Northstar's paid electricity cost, tariff, margin, or revenue.
- Public weather is contextual input, not evidence that weather caused a synthetic operational outcome.
- Public datasets must not be used to infer or reproduce personal travel, charging behavior, employee activity, confidential commercial terms, or another operator's internal performance.
- Scraped or undocumented sources are not accepted merely because a page is publicly viewable. Access and reuse terms must be reviewed and recorded.
- Live endpoint availability cannot be required for the core pipeline, tests, API, or UI demonstration.

### Ingestion requirements

Where terms permit, retain an immutable raw snapshot or a checksum-addressed retrieval artifact. If redistribution is prohibited, retain only the retrieval manifest, permitted derived fields, and instructions for an authorized user to retrieve the source. Never commit a restricted raw file to the repository.

Each ingestion must validate expected schema, record count, geographic and temporal coverage, accepted values, and source freshness. A later download is a new snapshot, not an in-place rewrite. Transformations must select a specific snapshot explicitly.

## SYNTHETIC OPERATIONS

### Required scope

Synthetic operations may include:

- Network, site, charger, connector, and asset attributes.
- Charging attempts and sessions, energy delivered, timestamps, and synthetic outcomes.
- Charger status, error events, telemetry, resets, and data gaps.
- Outages, failure episodes, restoration, and availability intervals.
- Maintenance events, work orders, inspections, actions, labor, and repair outcomes.
- Posted prices, pricing interventions, synthetic revenue, and synthetic energy costs.
- Parts catalogs, compatibility, approved substitutes, inventory, reservations, and movements.
- Purchase orders, shipments, receipts, synthetic suppliers, lead times, and prices.
- Part demand and usage associated with synthetic maintenance events.

All persons, organizations, assets, identifiers, transactions, amounts, operational histories, and relationships in this class are fictional. Synthetic data must not be generated by lightly modifying a confidential or personal dataset. Public aggregate distributions may inform generator assumptions only when their provenance and reuse terms are recorded and the resulting rows cannot be linked back to real people or confidential operations.

### Determinism and generator lineage

Synthetic data must be reproducible from a documented generator version, explicit seed, and versioned configuration. The generator should encode plausible relationships and known edge cases without claiming industry realism. Expected patterns—such as demand seasonality, price response, pre-failure telemetry, outages, late arrivals, or inventory shortages—must be documented so evaluation is not confused with discovery from a real network.

Generation runs must retain:

- Generator name and semantic or source-control version.
- Random seed and configuration version or checksum.
- Generation timestamp in UTC.
- Intended simulation start and end dates.
- Output schema version.
- Row counts and file or table checksums where practical.
- Parent run identifier when one generated dataset is extended or corrected.

The repository must provide a canonical seed and configuration for the portfolio demonstration. Additional seeds may be used for robustness checks, but they cannot silently replace the canonical evaluation data.

## Provenance contract

### Dataset-level manifest

Every source dataset or generated dataset must have a machine-readable manifest entry with these fields:

| Field | Requirement |
|---|---|
| `dataset_id` | Stable internal identifier. |
| `dataset_name` | Human-readable source or generated dataset name. |
| `data_class` | Exactly `PUBLIC_CONTEXT` or `SYNTHETIC_OPERATIONS`. |
| `provider_name` | Publishing organization for public data; `NOVA synthetic generator` for generated operations. |
| `source_url` | Canonical landing or documentation URL for public data; null for synthetic data. |
| `source_version` | Publisher release/version when available; generator version for synthetic data. |
| `retrieved_at_utc` | Actual retrieval time for public data; null if not retrieved. |
| `snapshot_date` | Frozen as-of date represented by the artifact or generation run. |
| `coverage_start` | Earliest represented observation or simulation time. |
| `coverage_end` | Latest represented observation or simulation time. |
| `license_name` | Published license name, or `NOVA-generated` for synthetic data. |
| `license_url` | Direct license or terms URL for public data; repository license reference for generated artifacts. |
| `terms_summary` | Concise record of attribution, redistribution, modification, and commercial-use constraints. |
| `attribution_text` | Required attribution exactly as it should appear, when applicable. |
| `redistribution_allowed` | `true`, `false`, or `unknown`; unknown data is not committed or redistributed. |
| `access_method` | Download, API, checked-in fixture, or generator command. |
| `artifact_uri` | Local artifact path or retrieval-manifest reference, not an undocumented live URL. |
| `artifact_checksum` | SHA-256 or equivalent for the frozen raw/generated artifact. |
| `schema_version` | Version of the expected source/output contract. |
| `owner` | Maintainer responsible for provenance and terms review. |
| `notes` | Known caveats, transformations, or restrictions. |

If a public provider publishes no clear license, record the applicable terms of use and treat redistribution as unknown until reviewed. Attribution alone does not establish permission to redistribute. A source version, license, or retrieval date that is unavailable must be stored as `unknown`, not guessed.

### Row-level provenance

Source-shaped tables must carry or inherit these fields at their documented grain:

- `data_class`
- `source_dataset_id`
- `source_snapshot_date`
- `source_record_id` when the public source supplies one
- `ingestion_run_id` for public ingestion or `generation_run_id` for synthetic generation
- `is_synthetic`
- `created_at_utc` or the pipeline timestamp appropriate to the record

For every SYNTHETIC OPERATIONS row:

- `data_class` must equal `SYNTHETIC_OPERATIONS`.
- `is_synthetic` must equal `true` and must be non-null.
- `source_dataset_id` must point to the generator manifest entry.
- `generation_run_id` must resolve to the seed, generator version, configuration, and generation time.
- Identifiers should use an unmistakably fictional namespace or prefix where practical, such as `syn_`, without relying on that prefix as the sole label.

For every PUBLIC CONTEXT row, `data_class` must equal `PUBLIC_CONTEXT`, `is_synthetic` must equal `false`, and the row must resolve to a public snapshot manifest. A null `is_synthetic` value is a contract failure, not an invitation to infer the class.

Derived dbt models may avoid repeating every source field when doing so would change the stated grain. In that case they must expose a documented lineage relationship to source manifest entries and include `contains_public_context` and `contains_synthetic_operations` flags. Mixed outputs normally set both to `true`.

### API and UI labeling

API responses that expose operational records or derived operational results must include a dataset or response-level disclosure equivalent to:

> Synthetic operations for a fictional charging network; not real customer or company performance.

Views enriched with public context must identify the public source and snapshot date in metadata or a provenance panel. The UI must not imply that a real public station is a Northstar asset. Downloads, screenshots intended for portfolio use, and reports must retain the synthetic disclosure.

## Snapshot-date policy

A snapshot date answers “which frozen edition of this dataset did this run use?” It is distinct from retrieval time and observation coverage.

- Public context uses the publisher's stated as-of or release date when available. Otherwise use the UTC retrieval date and record that the publisher supplied no explicit as-of date.
- Synthetic operations use the UTC date of the generation run as `snapshot_date`; simulation coverage dates remain separate.
- A pipeline run pins exact snapshot identifiers. It must not silently select “latest” during an otherwise reproducible build.
- Raw public snapshots and synthetic canonical outputs are immutable. Corrections create a new snapshot and record the superseded snapshot identifier.
- Model runs, reports, API readiness metadata, and portfolio result tables record all input snapshot identifiers.
- Documentation and screenshots state the snapshot date when the age of public context could affect interpretation.

## Licenses and terms to record

Before using any public source, record:

- Publisher and authoritative dataset title.
- Dataset landing page, documentation, and direct license or terms links.
- License name and version, if one exists.
- Required attribution and notice language.
- Whether raw data and modified or derived data may be redistributed.
- Restrictions on commercial use, automated access, rate, geography, or purpose.
- Retention, deletion, or update obligations.
- Whether station identifiers, coordinates, or other fields have special conditions.
- Date the terms were reviewed and the maintainer who reviewed them.
- Repository decision: commit snapshot, cache locally only, distribute derived fields only, or require user retrieval.

Terms can change. A new retrieval should verify that the recorded license or terms still apply. This policy records compliance evidence; it is not legal advice.

## Data-quality and leakage controls

- dbt source and staging tests verify non-null classification and synthetic labels.
- Relationship tests ensure every dataset and run identifier resolves to provenance metadata.
- Mixed marts document which columns originate from public context and which describe synthetic operations.
- Training features retain source snapshot and feature cutoff. Public records published after the prediction cutoff cannot enter a historical training example.
- Data-quality reports count unlabeled rows as contract failures and report their blast radius.
- Public values are not copied into synthetic target labels merely to manufacture model performance.
- Logs, fixtures, screenshots, and model artifacts are reviewed for accidentally included credentials, local paths, or unapproved source data before publication.

## Resume and portfolio claim policy

Claims must describe what the repository demonstrably implements, produces, and verifies. Architecture intent is not delivered functionality. A roadmap item is not an accomplishment. Synthetic results are not real-world business results.

### Claims that are prohibited

Do not claim or imply:

- **Real customers or users.** Northstar, its personas, drivers, technicians, and suppliers are fictional. A portfolio reviewer or local demo participant is not a production customer.
- **Real revenue, margin, savings, or operating costs.** All operational financial measures are synthetic-business proxies unless a public contextual value is clearly labeled otherwise.
- **Production deployment or production readiness.** Local Docker Compose, a hosted demo, or CI does not establish production security, reliability, scalability, governance, or operational use.
- **Measured business lift.** Scenario estimates, backtests, model accuracy, or generator-encoded effects are not recovered sessions, reduced downtime, revenue lift, cost savings, or causal impact at a real operator.
- **Real operational scale.** Do not describe the fictional site, charger, session, telemetry, outage, supplier, or inventory counts as a managed network or processed customer workload.
- **Impressive row counts that are unproduced or unverified.** Do not extrapolate, round up, quote an old run, count duplicated intermediates as new observations, or report a target data volume as achieved.
- **Autonomous decisions.** Recommendations and scenarios do not dispatch work, publish prices, transfer inventory, contact suppliers, or certify safety.
- **Causal conclusions from observational or synthetic correlations.** A constrained pricing scenario is not a field experiment unless an explicit experimental design was implemented and evaluated—and even then it remains synthetic evidence.

### Evidence required for allowed claims

A quantitative repository claim is allowed only when:

1. A documented command in a clean environment produces the underlying artifact.
2. The input snapshot, canonical seed, generator version, code revision, and relevant model or metric version are recorded.
3. An automated query, test, or evaluation verifies the exact number or result.
4. The grain and counting method are stated, so raw rows, unique events, features, and mart rows are not conflated.
5. Synthetic and public inputs are disclosed next to the claim.
6. The result is reproducible within the documented tolerance.
7. Limitations and the absence of real-world validation are not omitted.

For row-count claims, provide a checked query or generated summary by named relation or artifact, exclude duplicates according to its primary key, and state the snapshot. Phrases such as “million-row pipeline” are permitted only if the canonical repository run actually creates and tests at least that many rows at the claimed grain on the supported local path.

For model claims, name the target, horizon, temporal holdout, baseline, metric, eligible denominator, coverage, and synthetic nature of the evaluation. Training-set performance is not an acceptable headline result. For application claims, distinguish “implemented locally,” “tested in CI,” and “deployed”; use only the status evidenced by the repository.

### Acceptable phrasing

- “Built a local decision-support portfolio application for a fictional EV charging network using deterministic synthetic operating data.”
- “Implemented PostgreSQL and dbt models for defined network KPI proxies, with automated data-quality tests and visible unknown states.”
- “Evaluated a charger failure-risk model on a temporally held-out synthetic dataset; results are reported with calibration and coverage in the repository.”
- “Added optional public weather context from the recorded source and snapshot; all sessions and operating outcomes remain synthetic.”
- “The canonical seeded run generated and verified **N** unique session rows,” only when the repository's checked evidence supplies the value of **N**.

### Unacceptable phrasing

- “Improved customer revenue by 12%.”
- “Reduced charger downtime for a nationwide network.”
- “Deployed a production EV operations platform.”
- “Served millions of customers” or “managed thousands of chargers” based on generated records.
- “Processed 100 million rows” because the generator could theoretically be configured to do so.
- “Proved dynamic pricing increases demand” from a synthetic scenario or observational association.

## Claim review checklist

Before publishing a README result, case study, presentation, resume bullet, social post, or demo caption, verify:

- [ ] The named capability exists on the current default branch and is not only documented as planned.
- [ ] The referenced command succeeds using the documented supported setup.
- [ ] Quantitative values are generated and checked, with an artifact or query that a reviewer can reproduce.
- [ ] Dataset class, canonical seed or public snapshot, coverage period, and relevant code/model version are recorded.
- [ ] Counts name their table or event grain and deduplication rule.
- [ ] Model results name the temporal evaluation design, baseline, metric denominator, and coverage.
- [ ] Synthetic results are labeled synthetic in the same claim, not only in a distant disclaimer.
- [ ] Public context is attributed and does not imply ownership or operational performance.
- [ ] The wording makes no claim of real customers, revenue, business lift, or production deployment.
- [ ] Limitations and uncertainty are visible enough that a reasonable reader will not infer more than the evidence supports.

If any item fails, narrow the wording to the verified implementation or omit the claim until the repository supplies the evidence.
